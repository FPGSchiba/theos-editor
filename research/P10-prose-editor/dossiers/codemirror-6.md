## Byte-stable Markdown

- The source text is the document. The guide says "CodeMirror, being a text editor, treats the document as a flat string"; it is stored as a tree of lines, and positions are UTF-16 code-unit offsets [D11].
- No tree is serialized back. The Lezer Markdown parser only produces a syntax tree for styling and decorations; its README says it only parses the document and does not help with outputting HTML [D5]. The syntax tree is a side structure, so a Lezer node `from`/`to` is a document offset with no mapping layer [D11, D5].
- Edits are `ChangeSet`s (ranges plus inserted text) on the string. `ChangeSet.invert` and `compose` exist, and positions in a change set refer to the start document [D3, D11].
- Load and save without edits: `state.sliceDoc()` returned the identical string for an LF input in a probe [D54]. A UTF-8 BOM (U+FEFF) at the start survived the round trip [D54].
- Line endings are the one normalization. By default `\n`, `\r\n` and `\r` all split lines and lines are joined with `\n`, so CRLF or CR input comes back as LF unless a separator is configured [D3]. Probe results [D54]:
  - Default: a CRLF file read back as LF.
  - Mixed endings (`\r\n`, `\n`, `\r`) read back as all LF.
  - `EditorState.lineSeparator.of("\r\n")` plus `state.sliceDoc()` round-tripped CRLF identically; `state.doc.toString()` still joins with `\n` and did not.
  - `lineSeparator.of("\n")` on CRLF text round-tripped identically, because the `\r` stays inside the line text (whether the stock view draws that `\r` visibly was not tested).
  - With a configured CRLF separator, a plain `"\n"` inserted through `update({changes})` is not split and gives a lone LF in the text.
- Copy and cut read `state.sliceDoc(from, to)` (source text, including text under replace decorations), joined with `state.lineBreak`; with nothing selected the copy is line-wise [D2].
- Nothing in the stock view rewrites untouched text. The commands that add bytes are opt-in or Markdown-specific: `insertNewlineContinueMarkup` (Enter) continues list and blockquote markup, and `deleteMarkupBackward` (Backspace) replaces list markup with spaces. `markdown()` installs both unless `addKeymap: false`; it also installs an HTML tag completion source unless `completeHTMLTags: false` and `pasteURLAsLink` unless disabled (a paste of a URL over a selection becomes `[text](url)`) [D6].
- The view finds a user edit by reading the DOM and reporting a changed range (`inputHandler` receives "the document positions between which the change was found", with an `insert()` fallback transaction) [D2]. How tight that range is for autocorrect, spell-check replacement and IME commits is not documented; it is what the byte oracle measures.
- Undo and redo apply inverted change sets, so a document restored by undo is the earlier string [D3, D4].

## Front matter untouched

- Neither `@lezer/markdown` nor `@codemirror/lang-markdown` has front matter support (no occurrence of "front matter" or "frontmatter" in either package) [D5, D6]. A probe parse of `---\ntitle: x\n---\n\n# H` gave `HorizontalRule`, `SetextHeading2`, `ATXHeading1` [D54].
- A custom eager block parser can claim it. In a probe, a `BlockParser` placed `before: "LinkReference"` that checks `cx.lineStart == 0` and a `---` line, then consumes lines to the closing `---`, produced a `FrontMatter` node plus two `FrontMatterMark` nodes [D54, D5]. The API gives only `peekLine()` (one line ahead) for lookahead [D5]; an unclosed front matter swallowed the whole document in the probe [D54].
- `EditorState.changeFilter` is the documented protection hook: a filter returns `true`, `false` (drop the whole transaction) or an array of ranges `[from1, to1, from2, to2, …]` in which changes are suppressed. It runs for every transaction unless `filter: false` is set [D3].
- Measured boundary behaviour of `changeFilter` ranges `[0, fmEnd]` (probe, state 6.7.6) [D54]:
  - An insertion strictly inside the range is dropped.
  - A pure insertion at position 0 and at `fmEnd` is not dropped, so text typed before the opening `---` gets through.
  - A replacement spanning the range keeps the front matter but loses the inserted text (select all, type: the body was deleted and the typed text vanished).
  - A custom change filter that returns `false` when any changed range starts below `fmEnd` blocked the insertion at 0 and still allowed the insertion at `fmEnd`.
  - An `EditorState.transactionFilter` that clamps each change to start at `fmEnd` made select-all-and-type produce front matter plus the typed text, and moved an insertion at 0 to `fmEnd`.
- `transactionExtender` runs after the filters, can only add effects and annotations, and runs even when filtering is disabled [D3]. The history commands build undo and redo transactions with `filter: false` (`filter: false` in `HistoryState.pop`, commands 6.11.1), so change and transaction filters do not see undo or redo; those transactions are the inverse of changes that earlier passed the filters [D4, D3]. A filter therefore cannot veto an undo, for instance one that crosses a switch from Source mode (front matter editable) back to Write mode.
- Filters do not cover `view.setState(newState)`, which "reset[s] the view to the given state" and redraws everything [D2]. They only guard changes. `EditorView.atomicRanges` "does not prevent direct programmatic selection updates from moving into such regions" [D2].
- Hiding front matter in Write mode: `Decoration.replace` can "replace the given range with a widget, or simply hide it" [D2]. A replace that covers line breaks, or any block widget, must come from decoration sets provided directly (a state field), not from a function of the view, because those "are called after the new viewport has been computed" [D2, D11].
- Source mode in the same component: extensions can be swapped in one transaction with `Compartment.reconfigure`, without recreating the view [D3].
- Select-all-and-type and paste are ordinary transactions through the filters above [D3]. Backspace at the body start deletes inside `[0, fmEnd]` and is suppressed by the range filter; in the probe a deletion crossing `fmEnd` kept the front matter and applied only the part after it [D54]. The probe ran state-level transactions, not browser key events.

## Inline link chips

- Stock parse of `see [[id]] and [[id|text]]`: two `Link` nodes covering the inner `[id]` and `[id|text]`, the outer brackets are plain text [D54].
- A custom inline parser (`parseInline`, `before: "Link"`) produced one `WikiLink` node per link with child nodes `WikiLinkMark`, `WikiLinkTarget`, `WikiLinkMark`, plus `WikiLinkAlias` for `|text`; `[[…]]` inside backticks stayed `InlineCode` [D54, D5]. The API is documented: `MarkdownConfig.parseInline`, `InlineContext.addElement`, `elt`, and the bundled `Emoji` extension (a 10-line example) [D5].
- Maintainer statement on precedence: inline parsers are tried in order at the first character of a match, so a `[`-led construct preceded by `!` is claimed by the image parser; "you may not be able to parse this notation in combination with images" (issue lezer-parser/markdown #42, open as of 2026-04-15) [D31].
- No packaged Lezer or CodeMirror wikilink extension was found by `npm search "codemirror wikilink"` or `"lezer markdown wikilink"` on 2026-10-31 [D56]. `atomic-editor` (MIT, React, CodeMirror 6) exports a `wikiLinks` building block; its README does not mention IME [D49].
- Chip rendering: `Decoration.replace({widget})` over the whole `[[…]]` range, or `Decoration.mark` for styling only; `WidgetType` has `toDOM`, `eq`, `updateDOM`, `ignoreEvent` (default: ignore all events), `destroy`, `estimatedHeight` [D2]. Inline widgets are wrapped as `contenteditable="false"` elements, and CodeMirror draws a hidden `<img class="cm-widgetBuffer" aria-hidden>` beside uneditable widgets "to avoid a number of browser bugs that show up when the cursor is directly next to uneditable inline content" [D2 source].
- Caret steps over a chip as one unit only if the decoration set is also given to `EditorView.atomicRanges`; the docs say to do so "if you want decorated ranges to behave like atomic units for cursor motion and deletion purposes" [D2]. Atomic ranges make `moveByChar`, `moveVertically` and commands built on them skip the region [D2]. `deleteCharBackward` and `deleteCharForward` "take atomic ranges into account" (commands changelog) and `deleteBy` widens a deletion to the atomic range's edge [D4].
- Past atomic-range bugs, all closed in the GitHub snapshot: #1606 "Atomic range not working when right clicking" (closed 2025-09-01); #978, #939, #923 (atomic ranges, closed 2022) and #979 "Cursor navigation error when moving between adjacent widgets" (closed 2022-11-30) [D28].
- `[[` popover: `@codemirror/autocomplete` takes `override: CompletionSource[]`; a `Completion` has `label`, `detail`, `info` (DOM node or function), `type` (CSS class `cm-completionIcon-<type>`), `section`, `boost`, and `apply` as a string or `(view, completion, from, to) => void`; `addToOptions` injects DOM into each option; `activateOnTyping`, `closeOnBlur`, `tooltipClass` are configurable [D8]. Filtering by the kinds allowed at the caret is done inside the source function (it receives the context and the state). The popover DOM is the library's (`cm-tooltip-autocomplete`); a Svelte `LinkAutocomplete` would be mounted either in `addToOptions`/`info` fragments or as a separate `showTooltip` facet value whose `create(view)` returns `{dom}` [D8, D2].
- Broken-link state: any decoration source can read an index held in a state field and mark the chip with a class; no CodeMirror feature is specific to this [D2].
- Live Preview prior art (Obsidian): the Obsidian developer docs state that "Obsidian uses CodeMirror 6 (CM6) to power the Markdown editor", that an Obsidian editor extension "is the same thing as a CodeMirror 6 extension", and that changing how the document looks in Live Preview needs an editor extension [D41]. A forum user (ush) describes Live Preview as a state field whose decorations "display replace widgets when the cursor is not overlapping with the target positions" and, when overlapping, show syntax through mark decorations; another user (azito) notes extensions are "CodeMirror level" and cannot see what Obsidian adds on top, and that a replace widget they tried was not editable and integrated poorly with the editor [D44]. Obsidian's Live Preview source is not published [D44].
- Other open-source CM6 live-preview projects: SilverBullet shows syntax only near the cursor and has a toggle command [D47]; codemirror-rich-markdoc (MIT, 124 stars) hides syntax with a hidden class, replaces tables, blockquotes and Markdoc tags with block widgets, and its README lists as known issues that clicking inside rendered blocks may place the cursor at a mismatched position and that up/down navigation into rendered blocks can land at the opposite end [D48]; atomic-editor (README summary) hides markers on inactive lines without changing line heights and has a guard that skips decoration rebuilds during mouse clicks to avoid cursor drift [D49].
- IME prior art next to links in Live Preview: Obsidian 1.14.4 on macOS and Ubuntu, report of 2026-10-12: typing Japanese or Chinese IME "immediately after an external Markdown link" interrupts the first character's composition; thread tagged "tracked", no fix or reply shown when read [D45]. Windows IME with Chinese brackets jumped the caret in Live Preview (Obsidian 0.13.19, 2022-01); a forum user linked CodeMirror #652 and wrote it was fixed in Obsidian 0.13.25 [D46].

## Callouts with their own look

- Stock parse of `> [!voice] Hello there\n> more voice`: `Blockquote` with one `QuoteMark` per line and a `Paragraph` whose first child is a `Link` for `[!voice]`; `> [!note]- Title` parses the same way [D54].
- A custom inline parser at paragraph start (`pos == cx.offset`) emitted a `CalloutMarker` node for `[!type]`, `[!type]-`, `[!type]+`. An inline parser cannot see its parent block (the `InlineContext` API exposes text, offset and delimiters only), so `[!x]` at the start of a plain paragraph also matched in the probe; a decoration pass has to check for a `Blockquote` ancestor [D54, D5].
- Look per callout: `Decoration.line({class, attributes})` styles each `.cm-line` (each document line is its own `.cm-line` block, `white-space: pre`) [D2]; hiding the `> ` markers is `Decoration.replace({})` on the `QuoteMark` nodes [D2]. `EditorView.blockWrappers` (added in 6.39.0, 2025-12-08; `rank` option in 6.43.0) wraps a group of lines in one DOM element with a `tagName` and `attributes` [D2]. Block-wrapper composition bugs fixed in 6.39.15 (2026-02-20) and 6.42.1 (2026-05-07) [D2].
- Text stays editable in place because the callout is lines of ordinary text with decorations; a block replace widget instead hides the source range and its content is not editable by the editor ("block widgets … drawn between lines") [D2, D48].
- `Design note:` lines and developer-word flags: `MatchDecorator` maintains regex-based decorations on visible ranges inside lines; "will only be matched inside lines (not across them)", `boundary` and `decorate` options exist [D2]. Words flagged inside voice blocks need the Blockquote context, which the decorator does not provide; a view plugin over the syntax tree (as in the Obsidian Decorations example) can [D42].
- Obsidian decorations doc: mark decorations "style existing elements", widgets "insert elements in the document", replace decorations "hide or replace part of the document with another element", line decorations "add styling to the lines"; a view plugin "generally results in better performance" and can use `view.visibleRanges` [D42].
- Decoration sets that depend on the selection (raw under the caret, rendered elsewhere) can be rebuilt from `syntaxTree(state)` and `state.selection` inside a `StateField` provided to `EditorView.decorations`; a decoration set built inside a function is "called after the new viewport has been computed" and "must not introduce block widgets or replacing decorations that cover line breaks" [D2, D7].
- The Lezer tree can be incomplete for long documents: `syntaxTree(state)` returns "the current (possibly incomplete) parse tree"; `ensureSyntaxTree(state, upto, timeout=50)` and `forceParsing` complete it [D7].

## Beat headings with attribute lines

- Stock parse of `## Beat 1 — Opening\nactor:: [[npc-1]]\nmood:: calm\n\nText.`: `ATXHeading2` with `HeaderMark`, then one `Paragraph` covering both attribute lines (the lines merge into one paragraph node) [D54].
- A custom eager block parser (`before: "ATXHeading"`, regex `^key::[ \t]*value` on `line.text`) produced one `AttrLine` node per line with `AttrKey`, `AttrMark` (`::`) and `AttrValue` children [D54, D5]. Passing the value text to `cx.parser.parseInline(text, offset)` and adding the result as children of `AttrValue` gave `WikiLink` and `Emphasis` nodes inside the value [D54, D5].
- Editing one parameter changes only that line because the document is text and each attribute is one source line (see Byte-stable) [D11].
- Showing several `key:: value` lines as one `tu-beat` row: line decorations style each `.cm-line` separately; one row for several lines needs a block replace widget (which hides the source range) or CSS on `.cm-line`; no documentation or source found for the second option. Unknown for prototype [D2].
- Spans inside a line can be replaced by widgets (chips) with `Decoration.replace` and styled with `Decoration.mark`; per-line `attributes` allow `spellcheck="false"` [D2].
- A finding on a beat: `@codemirror/lint` accepts `Diagnostic {from, to, severity, markClass, source, message, renderMessage, actions}` and `setDiagnostics(state, diagnostics)` returns a transaction spec, so findings are pushed with `view.dispatch`; diagnostics are positions mapped through edits [D9]. Decorations from a state field and `StateEffect`s are the alternative [D3, D2].
- The lint extension adds mark plus widget decorations; it was the trigger of #1310, where a decoration update during a German-keyboard `^` dead key aborted composition (closed 2023-12-19) [D21, D9].

## Spell check and IME

Spell check
- The editable element is a `contenteditable` `.cm-content` with real text nodes inside `.cm-line` blocks; its stylesheet sets `-webkit-user-modify: read-write-plaintext-only` on `[contenteditable=true]` [D2 source].
- Defaults on the content element: `spellcheck="false"`, `autocorrect="off"`, `autocapitalize="off"`, `writingsuggestions="false"`, `translate="no"`. `EditorView.contentAttributes` "provides additional DOM attributes for the editable DOM element" and is merged over these defaults [D2 source and d.ts].
- A forum user turned native spell check on with `EditorView.contentAttributes.of({spellcheck: "true"})`: it worked on macOS Chrome and Safari, not on iOS (2022-03-14) [D38]. The maintainer's explanation: Safari does not run spell check "when the editable DOM is changed programmatically"; ProseMirror avoids DOM changes unless necessary; "I'm not aware of any other solutions" [D38].
- Report of 2026-09-05: with `contentAttributes.of({spellcheck: "true", lang: "en-US"})` on view 6.43.1 an editor got no native marks in Electron 44 (Chromium 152) while a plain contenteditable did; the maintainer saw spell checking work on Linux Chromium; the reporter concluded it was Electron's integration. A second user (2026-09-09) saw it on Chrome 152, unanswered in the thread [D37].
- Per-span opt-out: `Decoration.mark({attributes: {spellcheck: "false"}})` puts attributes on the elements holding the range; `Decoration.line({attributes})` does it for a line; widget DOM comes from `toDOM` and is made `contenteditable="false"` by the view [D2]. The HTML attribute is "merely a hint", inherited from the nearest ancestor with a state [D39]. No CodeMirror source says whether WebView2, WKWebView or WebKitGTK honour a nested `spellcheck="false"` for a span; Unknowns.

## Long documents

- Viewport rendering: "CodeMirror doesn't render the entire document, when that document is big"; it renders the visible part plus a margin; "Long lines (when not wrapped) or chunks of folded code can still make the viewport rather huge"; "Querying coordinates for positions outside of the current viewport will not work"; height information is tracked for the whole document [D11].
- Source constants (6.43.15): viewport margin 1000 px above and below the visible area; DOM height is scaled when the document height exceeds 7,000,000 px; horizontal gap cap 2,000,000 px [D2 source].
- No documented size limit was found. Obsidian's docs say "The Obsidian editor supports huge documents with millions of lines" because the editor "only renders what's visible (and a little bit more)" [D43].
- Text structure: tree of lines, "cheap edits anywhere" and cheap line lookup by number [D11].
- Parser budget: at state creation the language parses up to 3000 characters within a 20 ms budget; a background worker parses in idle slices of up to 100 ms with a 3000 ms budget per 30 s chunk, at most 100,000 characters beyond the viewport, and "will stop working when it has spent a certain amount of time or has moved beyond the visible viewport" [D7 source and d.ts]. `@lezer/markdown` reuses tree fragments incrementally; 1.8.1 (2026-10-19) "Improve incremental parsing performance by reusing entire groups of nodes", 1.6.3 (2026-01-06) fixed excessive re-parse after a list [D5].
- Decoration cost: sets built from a function can restrict work to the viewport (`view.visibleRanges`); sets provided directly (needed for block widgets and replaces over line breaks) are built over the whole document [D2, D42].
- Open issues (snapshot 2026-04-15): #1086 "Chrome scrollbar out of sync with height of long document" (opened 2023-02-22), #415 "Height scaling still has some issues" (2021-03-04), #1278 "iOS/Safari: Vertical scrollbar broken with many wrapped lines" (2023-10-06), #1663 "Unusual scrolling on some devices" (2026-01-23), #1693 lineWrapping click placement (2026-04-14) [D16].
- View 6.43.15 changelog: "Fix a division by zero in height scaling" and scroll stabilization fixes (2026-10-19) [D2].

## Svelte 5 integration

- No official Svelte binding was found: no Svelte package turned up under the `@codemirror` scope or in the CodeMirror docs read, and `@sveltejs/codemirror` returns 404 on npm [D55, D11, D12]. The view mounts into any element: `new EditorView({parent})`, `destroy()` "removing its element from the document, unregistering event handlers, and notifying plugins", unusable afterwards [D2].
- Community wrappers (npm metadata, read 2026-10-31) [D55, D50, D51]:
  - `svelte-codemirror-editor` (touchifyapp) 2.1.0, MIT, last release 2025-10-10, peers `svelte ^5` and `codemirror ^6`; v2.x is runes-only; 59,307 downloads in the week 2026-10-23 to 2026-10-29; GitHub 220 stars, 2 open issues (#43 dependency optimization, 2025-11-13; #28 build specifier error, 2024-01-09), not archived.
  - `@neocodemirror/svelte` 0.0.18 (2024-07-04, an action, no svelte peer), `codemirror-svelte` 2.0.0 (2023-06-04, peer `svelte ^3.50.1`), `svelte-codemirror` 1.2.1 (2022-05-19, ISC, Svelte 3).
- What `svelte-codemirror-editor` 2.1.0 does (source read) [D50]: `value` is `$bindable`; an external change to `value` calls `view.setState(EditorState.create({doc: value, extensions}))`, which rebuilds the state, so selection and undo history are not kept; editor changes are reported through `onchange`, debounced 300 ms unless `nodebounce`; it installs a large default extension set (line numbers, fold gutter, closeBrackets, autocompletion, default keymap, search keymap, lint keymap); `extensions` and `keybindings` props append more; `onready(view)` hands out the `EditorView`; an `$effect` reconfigures with `StateEffect.reconfigure` when props change; `{#if is_browser}` guards server rendering.
- `EditorView.setState` doc: "This will cause the entire document to be redrawn and all view plugins to be reinitialized, so you should probably only use it when the new state isn't derived from the old state" [D2].
- Widgets with Svelte components: `WidgetType.toDOM(view)` returns an element synchronously and `destroy(dom)` runs "when an instance of the widget is removed from the editor view"; `eq` and `updateDOM` avoid recreating the DOM [D2]. Svelte's `mount(Component, {target})` and `unmount(app, {outro})` are the imperative API; effects, `onMount` callbacks and actions "will not run during `mount`", and `flushSync()` forces pending effects; `unmount` returns a Promise (since 5.13.0) [D52]. A blog post (secondary source) mounts a Svelte 5 component in a CodeMirror panel with `mount(Find, args)` and shows no unmount [D53].
- Pushing index or finding changes without recreating the editor: `StateEffect.define` plus a `StateField`, `Compartment.reconfigure(ext)` (replaces one part of the configuration through a transaction), or `setDiagnostics` for findings [D3, D9]. `StateEffect.reconfigure` "does not reset the content of reconfigured compartments" [D3].
- External change as a minimal edit: `@codemirror/merge` 6.12.3 (MIT) exports `diff(a, b, config?)` returning `Change {fromA, toA, fromB, toB}` and `presentableDiff` (word-aligned) [D10]. In a probe (state 6.7.6, merge 6.12.3), applying `diff` hunks as `changes` with `annotations: Transaction.addToHistory.of(false)` kept the document equal to the external text, mapped the caret from 34 to 40 across edits before it, left `undoDepth` at 1, and `undo` reverted only the local edit [D54].
- History: `history()` from `@codemirror/commands`; `undoDepth(state)`, `redoDepth(state)`, `historyField`, `isolateHistory.of("before" | "after" | "full")` annotation, `Transaction.addToHistory.of(false)`, `invertedEffects`; config `minDepth` 100, `newGroupDelay` 500 [D4, D3]. There is no clear-history call: the maintainer wrote "You can't clear history" and advised creating a new state, or restoring a serialized history through `fromJSON` (2023-04-16) [D40]. In a probe, wrapping `history()` in a `Compartment` and dispatching `reconfigure([])` then `reconfigure(history())` gave `undoDepth` 0 and `redoDepth` 0; two edits marked `isolateHistory.of("full")` gave `undoDepth` 2 [D54].
- Keymaps: `keymap.of([{key, run}])`; `Mod-` is "a shorthand for Cmd- on Mac and Ctrl- on other platforms"; `mac`, `win`, `linux` fields override `key` per platform; a `run` returning `false` lets later bindings try; `runScopeHandlers(view, event, scope)` exists; `preventDefault` and `stopPropagation` flags per binding [D2]. Default bindings are opt-in: `historyKeymap` is Mod-z, Mod-y (Mod-Shift-z on macOS, Ctrl-Shift-z on Linux), Mod-u, Alt-u (Mod-Shift-u on macOS) [D4]. `markdown()` adds an Enter/Backspace keymap unless `addKeymap: false` [D6]. Binding lists can be built from data and passed as one `keymap.of(array)` [D2].
- Tooltips and popovers: `showTooltip` facet takes `Tooltip {pos, end, create(view)}`; `tooltips({position})` defaults to fixed positioning [D2].
- State of Svelte 5 combination: wrapper v2.x targets Svelte 5 runes [D50]; no official CodeMirror guidance for Svelte 5 widgets was found (Unknowns).
